# v4.6.2 PR3 — `models --check --live` probe Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** spec §6 (R2, D5) — an opt-in `--live` tier for `models --check`: one ordinary engine
leg per STORED alias, classified **served / accepted-but-silent / error**, the silent class
detected by PR2's no-output backstop with a 30 s override. Presence in the catalog is not proof
of service; this is the check that would have caught the v4.6.1 `gemini` incident outright.

**Architecture:** thread `noOutputBackstopMs` through `runFanout` → `runLeg` → `runHeadless`
(adding the recorded numeric-coercion guard at the `runHeadless` seam); a new
`src/sidecar/models-probe.js` builds ONE quiet fanout wave over the stored-alias targets and
classifies its legs; `runCheck` in `src/sidecar/models.js` gains the `--live` branch (spend
gate = the flag), human table + additive `probe` field on the audit doc.

**Tech Stack:** Node 18 CommonJS, jest, house patterns. Base: `main@7cbe293` (PR2 merged — the
backstop module and `options.noOutputBackstopMs` seam exist).

## Execution deviations (2026-08-04) — the durable record

Six corrections superseded or refined this plan's text during execution — five surfaced across
the Task 2→3 and Task 3→4 review cycles (one needed its own post-review doc fix), the sixth is
this document's own final-review blocker-fix commit. The plan body above is kept as written per
the anti-rot convention; THIS section is authoritative where they conflict. Full narrative and
live-smoke evidence live in `.superpowers/sdd/progress.md` (local-only) and the per-task reports
in the same directory.

1. **The CLI cap pre-check** (Task 2→3 review carry-in; `b9521df`). Not in the plan text. Task
   2's review found that a stored-alias count exceeding the fan-out leg cap
   (`DEFAULT_MAX_LEGS`/`AMICUS_FANOUT_MAX_LEGS`) would let `runFanout` fail wave-creation
   (`BAD_ARGS`) AFTER `models-probe.js` had already committed to the call — degrading every row
   to a generic error and losing the real reason. `runCheck` (`models.js`) now computes
   `selectStoredAliases(sources).length` and compares it against the same cap arithmetic
   `fanout-validate.js` uses, BEFORE calling `probeStoredAliases` at all: over-cap prints a
   one-line stderr error naming count/cap/env-knob and exits 1 with zero spend, never reaching
   the probe.
2. **Skip announcements + additive `probeSkipped`** (Task 3 review, Important; `4b02d4f`,
   doc-corrected in `0e6b386`). The plan didn't anticipate `--live` being silently dropped. Two
   paths could: the pre-existing catalog-unavailable early return in `runCheck`, and the
   `--refresh --check --live` short-circuit (`handleModels` routes to `runRefresh` before
   `runCheck` ever runs). Both now print a shared line via `fmtLiveSkipped(reason)` →
   `--live skipped: <reason> — nothing was probed`. The catalog-unavailable path additionally
   carries the reason as an additive `probeSkipped` field (null when the probe ran or `--live`
   wasn't requested) on the `alias-audit` `--json` doc (`buildAuditDoc`, mirroring the
   `drifted`/`driftedCount` pattern). The refresh path's `--json` output is a DIFFERENT document
   (`model-catalog`, via `buildCatalogDoc`) that was never widened to carry `probeSkipped` —
   that skip announces on **stderr** instead, keeping stdout valid JSON. A Task-4 review pass
   caught `docs/usage.md` overclaiming `probeSkipped` covered both paths; `0e6b386` split it
   into the two path-specific clauses above.
3. **SERVED rows are cost-only** (interface boundary, adjudicated correct in Task 3 review).
   The plan's illustrative human-output block showed `SERVED: gemini -> ... ($0.0004, 6s)` — a
   duration alongside cost. `probeStoredAliases()`'s (Task 2) return shape has no duration
   field, only `cost: number|null`, and Task 3's file list didn't include `models-probe.js`.
   The shipped `fmtProbeLine` (`models.js`) prints `($0.0004)` only. Recovering the duration
   would mean widening Task 2's already-landed interface; BACKLOG'd rather than decided
   unilaterally under Task 3.
4. **Task 4 reshaped into a `feat` commit, plus a post-review `docs` correction.** The plan
   scoped Task 4 as docs-only (`docs(v4.6.2-pr3): ...`). Execution rode three Task-3-review
   carry-ins along with it — the skip-announcement behavior in (2), a CLI parse-pin test, and
   exporting `selectStoredAliases` as the shared predicate the cap pre-check in (1) uses — all
   functional, not documentation, so the commit became `feat(models): announce --live skips +
   docs for the live probe` (`4b02d4f`). Its own review then caught the `docs/usage.md`
   overclaim described in (2); the one-line fix landed as a separate commit,
   `docs(models): probeSkipped is the catalog-path signal; the refresh path announces on
   stderr` (`0e6b386`), rather than an amend, per house policy on already-landed commits.
5. **`project: args.cwd || process.cwd()`, not a bare `opts.project` pass-through** (Task 3,
   `b9521df`; verified against the current `runCheck` body at time of writing). The plan's Task
   2 interface names the probe's own parameter `opts.project`; the CLI call site that actually
   supplies it resolves `args.cwd || process.cwd()` — there is no `--project`/`args.project`
   CLI flag. Stated here because the plan text could otherwise be misread as implying one.
6. **This commit — wave-level failure reasons surfaced, not fabricated** (final-review blocker
   1). Neither the plan nor Task 2/3 anticipated a wave failing BEFORE any leg is created. Two
   classes do: the budget preflight refusing pre-creation (`fanout.js`'s `failPre` →
   `{wave: null, errorDoc}`) and the shared OpenCode server failing to start (`errorWave` →
   `{legs: [], error: message}`). `probeStoredAliases` used to destructure only `{ wave }`,
   discarding `errorDoc`, and its `legs[i] || {}` fallback then fabricated
   `outcome: 'error', detail: null` for every stored alias — which `models.js`'s
   `${head} — ${r.detail}` template literal renders as the literal string `"null"`, silently
   (this wave always runs `quiet: true`) hiding the real reason from a `--live` user. Fixed by
   capturing `errorDoc` alongside `wave` and computing
   `waveFailure = errorDoc ? errorDoc.message : ((wave && wave.error) || null)`, then
   `detail: leg.error || waveFailure || null` per row — unconditional, not gated on outcome,
   because `waveFailure` is only ever non-null when `legs` is empty (no leg can classify
   'served' in that case), so the formula is equivalent to the old ternary wherever real legs
   exist and additionally correct on the two paths that have none. TDD: two new tests in
   `tests/sidecar/models-probe.test.js`, RED confirmed against pre-fix HEAD (both failed with
   the literal `detail: null` this fix removes), GREEN after.
