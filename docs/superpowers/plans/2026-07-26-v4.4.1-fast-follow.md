## Task 0: Settle line endings repo-wide

**This task ships alone, first, and its commit must be the only thing in it.** Every subsequent task writes new files; until this lands, an LF-ending file kills the pre-commit hook with an error that names neither line endings nor the file, and the failure looks like a git corruption rather than a formatting issue.

**Files:**
- Modify: `.gitattributes` (currently 3 lines: a comment + `*.sh text eol=lf`)

**Interfaces:**
- Consumes: nothing.
- Produces: a repo where any task may write a file with either line ending and commit it.

**Context:** `core.autocrlf=true` on this machine. lint-staged collects a command's output by iterating tinyexec's stream, which **merges stderr into stdout**, then feeds the result to `git rev-parse --short <hash>`. An LF-ending file makes `git stash create` emit `warning: in the working copy of 'X', LF will be replaced by CRLF…` on stderr; that warning lands in the captured "hash"; `rev-parse` rejects it. Root cause: `node_modules/lint-staged/lib/gitWorkflow.js:272` → `execGit.js`.

- [ ] **Step 1: Record the current state**

```bash
git config core.autocrlf
cat .gitattributes
git ls-files --eol | grep -c 'w/lf' || true
```

Capture the counts in the task report — the renormalization diff must be explainable.

- [ ] **Step 2: Write `.gitattributes`**

```gitattributes
# Normalize every text file to LF, in the object database AND the working tree,
# on every platform.
#
# Why this file exists: lint-staged captures a command's stderr INTO its stdout
# (node_modules/lint-staged/lib/gitWorkflow.js:272 -> execGit.js) and feeds the
# result to `git rev-parse --short <hash>`. A file with no explicit line-ending
# attribute lets core.autocrlf act on it, so `git stash create` prints
#   warning: in the working copy of 'X', LF will be replaced by CRLF
# on stderr, that warning lands in the captured "hash", and rev-parse fails with
# `fatal: Needed a single revision` -- naming neither line endings nor the file.
# An explicit declaration settles the question and the warning never fires.
#
# WHY eol=lf AND NOT eol=crlf: `eol=` is platform-independent -- it forces that
# ending in the working tree on Linux and macOS too, not just Windows. Under
# eol=crlf every executable text file needs a carve-out or it ships with a CRLF
# shebang: the kernel then looks for an interpreter named `node\r` and the
# program dies with "bad interpreter". This was not hypothetical -- the first
# cut of this task used eol=crlf and would have published bin/amicus.js (the
# `amicus`/`am` entrypoint, shipped via package.json files[]) with a CRLF
# shebang from publish.yml's ubuntu-latest runner, breaking the CLI for every
# Linux and macOS npm consumer. eol=lf needs no carve-outs at all.
* text=auto eol=lf

# Redundant under eol=lf, kept as explicit documentation of a hard requirement:
# `curl … | sh` breaks on a CRLF install.sh, and the husky hooks are bash
# scripts with no .sh extension, so a future change to the rule above must not
# silently reclaim them.
*.sh text eol=lf
.husky/* text eol=lf

# Binary assets: never touched. Keep this list complete -- text=auto's content
# sniffing usually catches an unlisted binary type, but "usually" is not the
# guarantee this block claims.
*.png binary
*.jpg binary
*.ico binary
*.woff binary
*.woff2 binary
*.ttf binary
```

- Produces:

  - The run's server is seeded with **RESOLVED executable ids**, never raw alias names — see **Step 8a**, which is not optional.
  - `run.json` carries exactly one of `sharedServer` `{acquired, at, goPid, models}` (acquired) or `sharedServerUnavailable` `{error, at}` (degraded), both declared in `schemas/council-run.schema.json` and documented in `docs/council.md`.

### What happened, measured

The council review of this plan (`output/v441-plan-council/`, run `v441plan01`) exited **1** with
`COUNCIL_QUORUM: Only 1 Stage-1 review(s) survived`. Four of five seats never ran a single leg.
`v441plan01-s1/metadata.json` records why:

```

database is locked
```

Wave created `23:06:35.493`, dead `23:06:36.229` — **736 ms, zero legs**. No orphaned OpenCode
process held the lock; this was a live startup race.

### Root cause

`src/council/run-stages.js:83` launches the Stage-1 seat wave and the critic solo together:

```js
const results = await Promise.all(launches);
```

Both call `runFanout`, and `src/sidecar/fanout.js:203` starts a server unconditionally:

```js
({ client, server } = await startOpenCodeServer(mcpServers, { models: … }));
```

There is **no** external-server seam in `runFanout`. So two waves 140 ms apart opened OpenCode's
SQLite (`~/.local/share/opencode/opencode.db`) simultaneously and the loser died.

`SharedServerManager` (`src/utils/shared-server.js`) already deduplicates concurrent starts
correctly via its `_starting` promise latch — but it is instantiated **only** in
`src/mcp-server.js:55`. The CLI path never touches it. Verified:

```bash
grep -rn "SharedServerManager" src/ --include=*.js   # → src/mcp-server.js only
```

### Why this belongs in 4.4.1 and not 4.5

Two reasons, and the second is the deciding one:

1. **It is not a new architecture.** One server shared across N legs is *already* what `runFanout`
   does inside a wave. This applies the existing pattern one scope level up — per run instead of
   per wave. `runHeadless` already has the seam to receive an injected server.
2. **The alternative is a limiting behaviour the user has to adopt.** Without this, `--critic` is a
   coin flip, and the workaround is "don't use the critic seat" — a documented feature made unusable
   by a race. A patch release that ships a workaround instead of the fix pushes the defect onto the
   user.

**It also makes every council run cheaper and faster.** A run currently starts a server for the seat
wave, the critic solo, *each* repair solo, the Stage-2 judge wave, *each* judge repair, each debate
wave, and the chair — 10+ process spawns, each one a fresh chance to lose this race.

⚠️ **The council-level fix cannot cover everything.** Two separate `amicus` processes, or a CLI run
alongside a live MCP server, still contend — which is why the bounded retry in Step 7 is part of
this task and not an optional extra.

- [ ] **Step 7: Make `startOpenCodeServer` survive a lock-class race**

The council fix does not help two separate `amicus` processes, or a CLI run beside a live MCP server. Both are real.

```js
// tests/sidecar/session-utils.test.js
test('a "database is locked" start failure is retried and can succeed', async () => {
  let n = 0;
  const spawn = jest.fn(async () => {
    n += 1;
    if (n === 1) { throw new Error('Unexpected error\n\ndatabase is locked'); }
    return fakeServerPair();
  });
  const pair = await startOpenCodeServer({}, { _spawn: spawn, retryDelayMs: 1 });
  expect(spawn).toHaveBeenCalledTimes(2);
  expect(pair.server).toBeDefined();
});

test('a non-lock failure is NOT retried', async () => {
  const spawn = jest.fn(async () => { throw new Error('ENOENT: opencode not found'); });
  await expect(startOpenCodeServer({}, { _spawn: spawn, retryDelayMs: 1 })).rejects.toThrow(/ENOENT/);
  expect(spawn).toHaveBeenCalledTimes(1);
});
```

⚠️ **Both tests above pass `retryDelayMs`, which is a TEST SEAM that collapses the whole
backoff schedule to one value. They pin the CLASSIFICATION (what is retried, and how many
times) and nothing about the timing.** They must not be read as pinning the window — see the
third test below.

Implement a **bounded** retry matching **only** a lock-class message (`/database is locked/i`,
`/database table is locked/i`, `/SQLITE_BUSY/i`). Never retry a missing binary, an auth
failure, or a port conflict: those are deterministic and a retry only multiplies the latency
before the same error.

**THE RETRY BUDGET — one value, stated once, here.** This is the only normative statement of
it in this plan; Step 10.5(b) is a historical note about how it got here and prescribes
nothing.

| | |
|---|---|
| Attempts | **5** (one initial + 4 retries) |
| Backoff schedule | **exactly `[250, 500, 1000, 2000]` ms** — each delay 2× its predecessor |
| Total added latency, worst case | **3,750 ms** |

Nothing about that is negotiable prose. "5 attempts with exponential backoff to ~4 s" is
satisfied equally by `250/500/1000/2000` (3.75 s), by `250/500/1000/2000/4000` (7.75 s) and by
`100/200/400/800/1600` (3.1 s) — so the sequence is written out as a literal, exported as
`LOCK_RETRY_DELAYS_MS`, and pinned by a test that **observes what the code actually sleeps**:

```js
// tests/server-setup.test.js — NO retryDelayMs: the seam would defeat the point.
test('the delays it actually SLEEPS are exactly 250/500/1000/2000', async () => {
  const slept = [];
  const real = setTimeout;
  const spy = jest.spyOn(global, 'setTimeout').mockImplementation((fn, ms) => { slept.push(ms); return real(fn, 0); });
  const attempt = jest.fn(async () => { throw new Error('database is locked'); });
  await expect(retryOnLockRace(attempt)).rejects.toThrow('database is locked');
  expect(slept).toEqual([250, 500, 1000, 2000]);   // ← disambiguates all three readings
  expect(attempt).toHaveBeenCalledTimes(5);
  spy.mockRestore();
});
```

⚠️ Asserting the exported constant is **not** sufficient on its own: an implementation that
ignores it (or applies it differently) leaves the constant test green. Pin the schedule as
executed. Also pin the negative — a deterministic failure must sleep **zero** times, not
merely fewer.

## Task 6: Abort the OpenCode session at the tool-settle ceiling

> **OWNER RULING (2026-07-26) on LC-2.** Keep the leg's completion and partial output exactly as they are, then **abort its own OpenCode session** so it stops billing. ⚠️ **Must be sequenced AFTER the child-session walk** or subtree attribution shipped in v4.4.0 is lost.

**Files:**
- Modify: `src/headless.js:501-525` (`deferForUnsettledTools`, the ceiling branch), and the finalization block near `:960-990`
- Test: `tests/headless-tool-stall.test.js`, `tests/observe/premature-completion.test.js`

**Interfaces:**
- Consumes: `abortSession(client, sessionId, directory)` from `src/opencode-client.js`; `walkChildSessions` from `src/sidecar/child-sessions.js` (added in `b848e6f`).
- Produces: `result.toolSettleAborted: boolean` alongside the existing `toolSettleTimedOut`.

**The reasoning to preserve.** At `headless.js:513-522`, exceeding `TOOL_SETTLE_GRACE_MS` (300 s default) sets `toolSettleTimedOut = true`, keeps the partial output, completes the leg, and surfaces the uncertainty on five channels. The session is left alone — and in the pathological case keeps billing. The original author declined to add an abort on a completion route because it "would stop the bleeding at the cost of truncating a possibly-healthy call."

**Why the ruling overrides that.** Once the leg has completed, `runHeadless` has returned and **nothing will ever read further session output**. Aborting after that point does not truncate an answer that would have been used — the outcome was already discarded by completing. What it stops is paying for work nobody will read.

**The sequencing constraint is load-bearing.** `runHeadless` walks each leg's child sessions at finalization, before `server.close()`. An abort issued before that walk risks losing the child-session cost data that `b848e6f` exists to capture — trading one silent under-report for another.
