## 1. Goal

An Electron **Council Workspace**: watch a council *think*, not just tail a log. One window that
shows, for any council run (live or historical):

- **Live reviewer progress** — per-seat status / stage / tokens / cost, from the v4.3 data layer.
- **Anonymized peer-review packets** — the exact Stage-2 bundle the judges saw, plus judge outputs.
- **Adjudication tiers** — Confirmed / Disputed / Contested / Singleton with the `basis {a,d,n}`
  counts and `thin` confidence, rendered truthfully per COUNCIL-DESIGN §5.2.
- **Dissent** — which judges disputed each finding, with rationale where captured.
- **Cost-by-seat** — per-seat usage/cost plus the whole-run `--max-cost` ceiling gauge.
- **One-click fold** of the chair result into Claude Code, reusing the existing fold mechanism
  (nonced `[SIDECAR_FOLD]` marker on the launcher's stdout).

Historical runs render entirely from the durable run directory (run.json + tally.json +
verdict.json + review/judge/chair files) — a cheap win independent of v4.3. Live runs add a poll
loop over the v4.3 snapshot API on top of the same rendering.

## 2. Non-goals

- **No new data collection.** v4.3 owns the data layer; the workspace only *reads* v4.0 run-dir
  artifacts and v4.3 snapshots. The workspace process **never writes into a run directory**.
- **No run editing.** Stage-4 decision *recording* stays with the skill / `amicus council verdict
  --decisions`; the workspace *displays* decisions when present in verdict.json.
- **No policy-pack authoring or launch configuration** (v4.5). No "launch a council" surface.
- **No web/remote serving.** Local Electron only; no HTTP listener, no remote access.
- **No wave (plain fanout) workspace view in v1.** `amicus watch` (v4.3, terminal) covers waves;
  the workspace is council-shaped. Council-run stage waves ARE shown (as seats of their stage).
- **No packaged/installer app.** Ships inside the same unpackaged Electron app, provisioned
  lazily via `ensureElectron()` (#55 precedent, `src/sidecar/setup-window.js`).
- **No MCP launcher tool in v1** — tool-count discipline holds at 15; Claude launches the GUI via
  the CLI. (Open question 5.)
- **No `--json` mode for the `--ui` command** — interactive-only, added to the documented
  envelope exclusions alongside `setup`/`update`/`key` (v4.0 §2).

## 4. Architecture

### 4.1 Window model — third Electron mode, dedicated window (recommended)

`AMICUS_MODE=council-workspace` joins `sidecar`/`setup` in `electron/main.js`'s mode switch. One
`BrowserWindow` (~1100×800, min 860×600), no `WebContentsView` split — the workspace is a single
first-party page, not embedded foreign UI.

**Rejected alternatives:**
- *A view inside the existing sidecar shell* — the shell's lifecycle is one interactive sidecar
  session (spawned by `amicus start`, bound to an OpenCode server + session route). Councils are
  headless runs with no OpenCode UI; coupling the two lifecycles buys nothing and complicates the
  close-guard/fold semantics that shell already carries.
- *Local HTTP server + system browser* — violates the no-web-serving non-goal, adds a listening
  surface, and loses IPC (fold/abort) integration.
- *Make report.html live (self-polling)* — report.html is a deliberately inert, shareable
  post-run artifact; `file://` pages can't re-read sibling files without loosening exactly the
  restrictions we want kept. Keep the report static; the workspace supersedes it on-screen.

### 4.2 Renderer loading + sandbox posture (M9-consistent)

**Static files via `loadFile`, `sandbox: true`, `contextIsolation: true`, `nodeIntegration:
false`.** New `electron/workspace-ui/` with `index.html`, `workspace.css`, and renderer JS
(split to respect the 300-line gate, e.g. `workspace-app.js`, `workspace-render.js`,
`workspace-matrix.js`).

Why not the setup-wizard pattern (data: URL + `sandbox: false`)? Two reasons:

1. **The data:-URL contextBridge trap** (`docs/electron-testing.md` Known Limitations):
   `contextBridge.exposeInMainWorld` silently fails for data: origins under sandbox — the toolbar
   works around it with `executeJavaScript` polling, and setup only works because it runs
   `sandbox: false`. `loadFile` (a real `file://` origin) supports contextBridge under full
   sandbox — no workaround, no polling hack.
2. **The workspace renders untrusted model text** (reviews, judge prose, chair output — the H9
   threat surface v4.0 fenced on MCP). Setup renders only local config; the workspace must be the
   *most* locked-down page in the app, not the least. `sandbox: false` + a shell-capable preload
   (preload-setup.js) would be a posture regression.

Renderer hardening:
- `preload-workspace.js` (new): contextBridge exposes exactly
  `window.amicusWorkspace = { invoke(channel, ...args) }` with a hardcoded channel allowlist
  (preload-setup.js pattern), **no `shell`**, nothing else.
- `will-navigate` → `event.preventDefault()` always (the page never navigates);
  `setWindowOpenHandler(() => ({ action: 'deny' }))` — same guards as the content view (M9).
- CSP `<meta>` in index.html: `default-src 'none'; script-src file:; style-src file:
  'unsafe-inline'; font-src file:; img-src file: data:` (file: scheme needs explicit `file:`
  sources; no network directives at all).
- **All model-derived strings enter the DOM via `textContent` / DOM-node construction — never
  `innerHTML`.** Prose panels use a dependency-free "markdown-lite" formatter (headings, bullets,
  fenced code → styled elements, all text via `textContent`); zero runtime deps added, no HTML
  passthrough.
- Design tokens: `index.html` links the shared token file **relatively**
  (`<link href="../../src/design/tokens.css">`) — on `file://` the `./fonts/*.ttf` URLs inside
  tokens.css resolve correctly relative to tokens.css itself, so the bundled Outfit/IBM Plex Mono
  load with **no** `absoluteFontUrls` rewrite and no `insertCSS` needed. `workspace.css` uses
  token vars only (single-token-source rule from the design-system plan).

### 4.3 Process model & data flow

```
amicus watch <runId> --ui            (CLI, per A5 — or `council watch --ui` fallback)
  └─ src/sidecar/workspace-window.js (new launcher; setup-window.js pattern:
     ensureElectron() → spawn(electron, [main.js]) with env, stdout piped)
       env: AMICUS_MODE=council-workspace, AMICUS_PROJECT=<cwd>,
            AMICUS_RUN_ID=<runId|''>, AMICUS_FOLD_NONCE=<generated per launch>,
            AMICUS_DEBUG_PORT / AMICUS_HEADLESS_TEST passthrough
  Electron main (electron/main.js mode branch)
    ├─ electron/ipc-workspace.js (new; ipc-setup.js pattern) — all handlers
    │    delegate to pure modules in src/workspace/ (unit-testable headless):
    │    run-scan.js (pointer-file walk → run list), run-detail.js (read+parse
    │    run.json/tally.json/verdict.json defensively), artifact-guard.js
    │    (allowlist + realpath containment), fold-format.js (fold text builder),
    │    plus the v4.3 snapshot API (A1) for live data
    └─ BrowserWindow → loadFile(electron/workspace-ui/index.html)
         renderer polls via invoke() — renderer-driven, visibility-aware
```

- **Reads are main-process-side.** The renderer never sees a filesystem path except for display;
  it requests data by `runId` + allowlisted artifact name.
- **Poll transport (renderer-driven):** active visible run → `workspace:get-live` every **1.5 s**;
  window blurred/hidden → 5 s; run reaches terminal status → stop polling, do a final
  `workspace:get-run`. Run list refreshes every 5 s and on window focus. (Per A7, poll is the
  contract; push is a compatible later swap.)
- Run discovery: pointer files `council-<runId>.json` (`{runDir}`) in
  `<project>/.claude/amicus_sessions/` (v4.0 §4), then `run.json` inside each `runDir`. Pointer
  targets are user-trust (same machine, same user) but artifact reads are still realpath-pinned
  inside the resolved `runDir` (defense-in-depth).

### 4.4 CLI entry point

Primary: **`amicus watch <councilRunId> --ui`** and bare **`amicus watch --ui`** (opens on the run
list) — riding v4.3's watch verb per A5, so terminal-watch and GUI-watch are one concept with one
spelling. Fallback if v4.3 scopes `watch` wave-only: `amicus council watch --ui [runId]`.
Handler: thin `--ui` branch that calls `launchWorkspaceWindow()` and relays child stdout (the fold
channel) to its own stdout, exiting with the child's code. Interactive-only; no `--json`.

**Rejected:** a toolbar entry in the sidecar shell (different lifecycle, and sidecar sessions
usually outlive no council); a standalone `amicus workspace` verb (second spelling for the same
concept).

### 4.5 IPC surface (exact channels)

Namespace `workspace:` (parallel to `sidecar:`). All handlers registered in
`electron/ipc-workspace.js`; every handler validates the sender against the workspace window's
webContents via the shared `isPrivilegedSender` helper (`electron/ipc-guard.js`) — same
belt-and-suspenders as the sidecar handlers, even though this window has only one webContents.

| Channel | Args → Returns | Notes |
|---|---|---|
| `workspace:list-runs` | `()` → `[{runId, runDir, status, startedAt, completedAt?, bench, chair, tierCounts?, overallVerdict?, cost?}]` | pointer-file scan + shallow run.json/verdict.json read; unreadable runs come back `{runId, error}` rows, never throw |
| `workspace:get-run` | `(runId)` → `{run, tally?, verdict?, artifacts: {name: {present, bytes}}}` | terminal/static snapshot; defensive parse — malformed JSON yields `{parseError, rawPath}` per document |
| `workspace:get-live` | `(runId)` → v4.3 live snapshot (A1) | the poll hot path; must not re-parse conversation.jsonl per tick (A1 cheapness) |
| `workspace:read-artifact` | `(runId, name)` → `{text, truncated?}` | name must match the run's manifest-derived allowlist (see the note below this table); realpath must stay inside runDir; >200 KB truncated with notice |
| `workspace:abort-run` | `(runId)` → `{ok, error?}` | delegates to the existing v4.0 abort path (council-aware `amicus abort` internals) with `AMICUS_PROJECT`; renderer confirm-gates it |
| `workspace:fold` | `(runId)` → `{ok}` | §7; latch against re-entry |
| `workspace:open-report` | `(runId)` → `{ok}` | main-process `shell.openExternal(pathToFileURL(report.html))` — only for the run's own `report.html`, existence-checked; keeps foreign HTML out of the app window |

No main→renderer push channels in v1 (poll covers it); `workspace:live-update` is reserved as the
A7 upgrade seam.

**The `workspace:read-artifact` allowlist** (corrected 2026-07-27, v4.4.1 DOC-4 — this table used
to name a flat 7 files, which is what made the shipped guard hard-refuse every `--debate` output
until F28 was fixed). It is derived per run, not fixed. Truth:
`src/workspace/artifact-guard.js` — `FIXED_ARTIFACTS`, `DEBATE_ARTIFACTS` and `artifactAllowlist`.

| Group | Names | When |
|---|---|---|
| `FIXED_ARTIFACTS` (5) | `briefing-stage1.md`, `bundle-stage2.md`, `chair-packet.md`, `chair-output.md`, `tally-input.json` | always |
| `DEBATE_ARTIFACTS` (3) | `tally-provisional.json`, `revote-bundle.md`, `debate.json` | only when `run.json` carries a `debate` key (a `--debate` run) |
| per bench model | `review-<model>.md`, `judge-<model>.md` | always, one pair per entry in `run.json`'s `bench` |

`<model>` is the bench alias through `sanitizeName` (`src/council/run-launch.js`), which strips

`collisions` array rather than silently deduping (see RN-1). `report.html` is deliberately absent —
it opens externally via `workspace:open-report`.

## 5. UI structure

Two screens, one window. Left rail = run list; main area = run detail. Direct-launch with
`AMICUS_RUN_ID` set opens straight into that run's detail.

### 5.1 Run list (left rail / landing)

- One row per council run in the current project (`AMICUS_PROJECT`): runId (short), started
  relative time, status chip (`running` pulse / `complete` / `partial` / `error` / `aborted`),
  bench size, chair (or blind label, §6 — amended 2026-07-25: masked when a label is known for
  it, in practice only for the currently-open run's own row), overallVerdict chip when present,
  cost.
- Sort: startedAt desc. Unreadable runs render as inert error rows with the raw path.
- Cross-project browsing is out of v1 (pointer files are per-project; Open question 8).

Renderer behavior: artifact panels lazy-load on first open (`workspace:read-artifact`) and cache
with mtime invalidation; seat rows update keyed (no full re-render per tick); prose renders as a
single formatted block (fast even at tens of KB); >200 KB artifacts truncate with an
"open folder" affordance.

### 5.3 Design system, theming, accessibility

- Single token source: everything from `src/design/tokens.css` vars (clay/gold on neutral-black;
  tier light-ground + ink pairs; provider colors for seat avatars/dots). No new hex anywhere
  (design-system plan Global Constraints).
- Dark-only, matching the app (the design system is a dark-ground system; report.html's
  light-ground tier palette is reused *as token vars* for matrix rows exactly as report-html.js
  does).
- Status never by color alone: chips carry text; matrix cells carry symbols (✓/✗/○) with
  `title`/`aria-label` text.
- Keyboard: run list arrow-key navigable; panels tabbable; `--focus-ring` focus-visible styles;
  Esc dismisses dialogs (abort confirm). `prefers-reduced-motion` disables the running-pulse.
- Type: `--font-sans` UI, `--font-mono` for ids/models/costs — matching toolbar/report precedent.

### 5.4 Performance envelope

Bounded by design: benches cap at `DEFAULT_MAX_LEGS = 10` seats
(`src/sidecar/fanout-validate.js`), so seat rows and matrix columns never exceed 10; findings run
~10–60 rows typical, a few hundred worst-case — plain keyed DOM is sufficient, **no
virtualization in v1** (matrix hard-caps at 500 rendered rows with a "show more" expander as a
safety valve). The poll hot path touches only small files via the v4.3 snapshot (A1); prose files
load lazily per panel. Re-render is diffed per seat/stage hash.

## 6. Anonymity rules in the UI

Grounded in the v4.0 model (§6): the label↔model map lives in orchestrator memory and `run.json`;
judge legs are cwd-pinned to `_scratch/` and never see de-anonymized files; the chair packet
de-anonymizes by design.

1. **The GUI is on the orchestrator side of the trust line.** The user owns the run dir and can
   read `run.json` (which contains `labelMap`) in any editor; hiding identities from the user is
   therefore *bias hygiene*, not security. The spec says this out loud so nobody later mistakes a
   UI toggle for a security control.
2. **The security-relevant invariant the GUI must uphold:** the workspace **never writes into the
   run directory** (read-only posture end to end) — so it can never leak the map into a
   judge-visible file, and never perturbs `_scratch/` isolation. Enforced structurally: no IPC
   channel has write semantics against runDir; fold/abort write elsewhere (stdout / sessions
   metadata via the engine's own abort path).
3. **Blind mode (reading aid).** A per-window toggle maps model ids ↔ labels (`Review A`…)
   everywhere they co-occur with review authorship (seats, reviews list, matrix raisers/judges,
   street-cred rows), using run.json `labelMap`. Defaults: **ON while a run is live and
   non-terminal** (read the packet the way the judges did; finding ids like `A1` already use
   label-space, so blind mode is the *native* display for Stage-2 data), **OFF for terminal
   runs** (matching report.html, which is fully de-anonymized). Toggle state is per-window,
   never persisted.
   > **Amendment (Christian, 2026-07-25 — fourth live paid council review, renderer surface,
   > major, unanimous):** "everywhere they co-occur with review authorship" now explicitly
   > **includes the header chips (bench/critic/chair) and the run-list rail's chair chip** —
   > a fourth council review found both bypassing the shared `display(pair, blind)` formatter
   > and interpolating raw model ids directly, an inconsistency with the (correctly masked)
   > seat table on the very same screen. This supersedes the reading recorded under Resolved
   > question 2 below, which read the unmasked header/rail as correct-by-design on the theory
   > that blind mode hides only *which model wrote which review*, not the roster itself.
   > Christian's ruling: **blind mode IS for masking the roster.** The "reading aid, not
   > security" framing (point 1 above, unchanged) still holds — masking degrades gracefully to
   > the raw id wherever no label is known (e.g. an unopened run's row in the run list), which
   > is exactly the *reading aid* posture, not a hard guarantee.
4. **The Stage-2 packet renders verbatim** (`bundle-stage2.md` as written) — the workspace shows
   what judges actually saw, and never a reconstructed variant. De-anonymization is presented
   *around* it (legend when blind mode is off), never *edited into* it.
5. **Live-vs-post-run visibility decision:** nothing is withheld live — seat identities, spend,
   and stage progress are the user's own operational data (the roadmap's "live reviewer
   progress" headline). Only the *default* presentation changes (blind ON live), and the
   chair-packet artifact (which contains identities inline) is browsable at any time via the
   artifact list for users who want it.

## 7. Fold integration (reuse, not reinvention)

The existing mechanism (`electron/fold.js` + `src/utils/fold-marker.js`): Electron writes a
nonced `[SIDECAR_FOLD:<nonce>]` marker line + summary to **its stdout**, the spawning CLI relays
it, and Claude Code reads the command output. The workspace reuses the marker/nonce/stdout
contract exactly; what changes is that **no model summarization call is needed** — the chair
result already exists on disk, so a workspace fold is a fast local read+format (milliseconds).

- The launcher generates a per-launch nonce (`generateFoldNonce()`), passes it as
  `AMICUS_FOLD_NONCE` (same env contract as the sidecar), and the CLI wrapper relays child stdout.
- `workspace:fold` (button on the Verdict panel, always enabled once run.json exists) →
  `src/workspace/fold-format.js` builds:

  ```
  [SIDECAR_FOLD:<nonce>]
  Model: <chair model>
  Session: <councilRunId>
  Client: council-workspace
  CWD: <project>
  Mode: council
  ---
  VERDICT: <chair line | none>
  Tiers: Confirmed N · Disputed N · Contested N · Singleton N
  Cost: $X.XX (<source>)
  <chair-output.md body>
  ```

- **The chair body is untrusted model text**, so it is passed through v4.0's
  `stripFoldMarkers()` before embedding — chair prose containing a marker can never truncate or
  spoof the fold (the exact hazard the v4.0 nonce-closure exists for).
- **Degraded fold** mirrors the engine's degradation table: chair missing / `overallVerdict:
  null` → `VERDICT: none` + tally summary; pre-tally → stage/status summary only. Never blocked,
  always labeled.
- **Close semantics:** unlike the sidecar (close-guard B01 auto-fold), the workspace is a
  *viewer* — closing without folding is a legitimate exit (browsing history) and triggers
  **no auto-fold**. The only guard kept is a minimal in-flight latch: while a fold is being
  written, `close` is prevented until the stdout write settles (a two-flag reuse of the
  `isFolding()/hasCompleted()` pattern, without the fallback-destroy machinery — folds here do
  no async model work, so the failure surface close-guard.js exists for doesn't apply).
- Exit codes: 0 on fold-then-close and on plain close; the CLI wrapper propagates.

## 8. Control surface — read-only viewer + two verbs (v1 scope)

**Recommendation: viewer + Abort + Fold. No launch.**

- **Abort** (header button, live runs only): confirm dialog → `workspace:abort-run` → the
  existing council-aware abort path (v4.0 §4: mark run.json aborted + cascade to active
  wave/solo taskIds). Zero new mutation logic; it is the remedy for the dead-run state the
  workspace itself surfaces (§9), and it serves the v4.3 arc's "never waste a run" theme.
- **Fold** (§7).
- **Launch rejected for v1:** a launch surface drags briefing-file pickers, seat/chair/lens
  configuration, and cost preview into 4.4 — that's v4.5 policy-pack territory (invoke-by-name
  is what makes a launch GUI sane) plus the backlogged `--dry-run` cost preview. A pure viewer
  (zero verbs) was also rejected: it would show you a wedged run and offer no way out.

## 9. Error / degraded states

The engine's degradation ladder (v4.0 §4) is rendered, never papered over:

| State | Detection | Workspace behavior |
|---|---|---|
| run.json missing/unparseable | read/parse fail | run-list error row; detail shows raw path + "open folder"; no crash (all parses defensive in main) |
| Unsupported schema | `schemaVersion !== 2` on run.json/tally/verdict | banner "run written by a different amicus version" + artifact paths; panels that can't trust shapes stay empty |
| **Dead run** | ⚠️ **A4 is FALSE on shipped v4.3 — see the §3 banner.** There are no `stalled`/`crashed` flags on the council payload; crash surfaces as `status:'error'` + `reason`. Keep "never GUI-invented": either take the flags plan Task 0.5 computes, or key the banner off `status`/`reason` — do not derive liveness in the renderer | red banner "no leg activity for Xm — the run may be dead", Abort offered; everything already on disk stays browsable |
| Quorum failure (exit 1, `council_quorum`) | run.json status error + error doc | error panel with the engine's message; surviving Stage-1 reviews browsable |
| **Partial wave** (exit 2) | status + `judged: false` / reduced judge set | amber badges naming exactly what's missing ("2 of 4 judges completed — tally is peers-reduced"); matrix renders over surviving judges (tier rules already count engaged judges — COUNCIL-DESIGN §8) |
| **Missing chair** / `overallVerdict: null` | verdict.json | Verdict panel: "no chair verdict" + reason from run.json (chair failed after retry+promotion / repair failed / ceiling hit); chair prose shown if any; fold degrades per §7 |
| Cost ceiling hit | run.json usage vs `options.maxCost` + skipped-stage reason | gauge turns `--danger`, banner states which stage was not launched |
| Aborted | status `aborted` | grey chip; artifacts browsable; no live poll |
| Expected artifact missing | `workspace:get-run` manifest flags | per-panel empty state naming the exact file (e.g. "bundle-stage2.md not written yet") |
| Electron missing at launch | `ensureElectron()` fails | CLI prints the same actionable error as setup; nothing half-opens |
| v4.3 snapshot API errors | A1 call throws | seats panel falls back to last-known + "live data unavailable" chip; static panels unaffected |

   > actually masks), and the implementation that shipped read that silence as "seats and

   > implicit is now resolved. Preserved verbatim per this file's own convention of not
   > silently rewriting history.

3. **Fold-on-close: should closing the workspace ever auto-fold (sidecar B01 behavior)?**
   **Recommendation: no auto-fold — viewer semantics.** The sidecar auto-folds because closing
   discards an unsaved model summary; the workspace discards nothing (all artifacts are on
   disk, and the fold is reproducible any time by reopening). Auto-folding on every browse of a
   historical run would spam the launching terminal. Keep only the in-flight close latch.

4. **Entry-point spelling: `amicus watch --ui [runId]` (riding v4.3's watch verb, per A5) or a
   separate `amicus council watch --ui`?**
   **Recommendation: `amicus watch --ui`** — one verb for "look at a run," terminal by default,
   `--ui` for the window, council runIds accepted exactly like status/wait/list. Fall back to
   `council watch --ui` only if the v4.3 spec scopes `watch` to waves.

5. **MCP launcher tool (`amicus_council_watch`) in v4.4?**
   **Recommendation: no — defer.** Tool-count discipline (the 52→13 de-bloat, now 15) is worth
   protecting; Claude can launch the GUI via Bash (`amicus watch <runId> --ui`) and read the fold
   from the command output exactly like an interactive sidecar. Revisit on Cowork-mode demand,
   where Bash may be unavailable.

6. **Should plain fanout waves appear in the run list in v1, or council runs only?**
   **Recommendation: council-only v1.** The workspace's panels (packets, tiers, dissent, chair)
   are council-shaped; a wave row would be two columns of the seats panel and nothing else, and
   v4.3's terminal `amicus watch <waveId>` already covers it. Adding waves later is additive
   (`kind: 'wave'` is already in the A1 snapshot shape).

7. **Model-prose rendering depth: markdown-lite (headings/bullets/code fences, textContent-only)
   or plain preformatted text in v1?**
   **Recommendation: markdown-lite.** Reviews and chair output are long structured markdown;
   pure `<pre>` makes the flagship panels markedly worse to read. The formatter is
   dependency-free and never touches innerHTML, so the security posture is identical to plain
   text. If you want v1 even leaner, plain text is the acceptable fallback — the seam is one
   renderer function.

8. **Run-list scope: current project only (as specced) or a cross-project registry?**
   **Recommendation: current project only.** Pointer files live in the per-project sessions dir;
   a cross-project registry means a new global index file — that's new data collection, which
   v4.4 forswears (v4.3 owns data). If cross-project browsing matters, it should enter the v4.3
   contract as a listing API first.

9. **Window sizing/position: fixed default (~1100×800, centered) or reuse the sidecar's
   `AMICUS_WINDOW_POSITION` right-dock convention?**
   **Recommendation: fixed default, centered, resizable, position remembered per session only.**
   The sidecar docks right to sit beside Claude Code during a conversation; the workspace is a
   destination you open deliberately and read — centered large is the better default, and
   persisting window bounds is config surface we don't need yet.
