## Item 2 — bearer CR/LF sanitize + `0600` re-assert

**Defect.** Both the local-provider bearer writer (`saveRawEnv`) and the static-vendor
key writer (`saveApiKey`) funnel through one chokepoint, `upsertEnvLine` /
`deleteEnvLine` in `src/utils/env-raw-store.js`. Two gaps:

1. **No sanitization.** A token carrying CR/LF (paste, `echo key | ...`) is written
   verbatim into the line-based `.env`. A trailing `\r\n` produces a spurious blank
   line and bakes a trailing CR into the served token; an interior newline *truncates*
   the token on read (`sk-\r\nsecret` → `sk-`). `process.env` also kept the raw value.
2. **`0600` not re-asserted on existing files.** `fs.writeFileSync(path, ..., {mode:
   0o600})` applies the mode only on **create**; rewriting an existing `.env` whose
   perms drifted (created under a loose umask, or hand-edited) never re-tightens.

**Fix (single chokepoint, covers both writers).**
- `upsertEnvLine` strips `[\r\n]` from the value (`clean`), writes `clean`, and
  **returns** it. Bearer/API-key schemes never contain newlines, so stripping cannot
  damage a legitimate token. `saveApiKey` and `saveRawEnv` mirror the **cleaned**
  value into `process.env`.
- `upsertEnvLine`, `deleteEnvLine`, and `migrateEnvFileKey` each add a best-effort
  `fs.chmodSync(path, 0o600)` after their `writeFileSync` to re-tighten an existing
  secrets file. Best-effort (a documented no-op on Windows/NTFS).

**Decision — strip vs reject:** strip. Matches the deferral wording, lowest-risk, and
handles the common accidental trailing newline without turning a recoverable paste into
a hard CLI error.

## Item 3 — global hermetic test baseline

**Defect.** Tests that reach a real config/probe path resolve config via
`getConfigDir()` / `getEnvPath()`, which read `AMICUS_CONFIG_DIR` / `AMICUS_ENV_DIR`
from `process.env` and otherwise fall back to the real `~/.config/amicus`. A test that
forgets to pin those vars can read — or clobber — the developer's real config/keys. This
was hit and patched per-test repeatedly during v4.2.

**Fix.** A global `setupFiles` module (`tests/setup/hermetic-config-dir.js`, wired in
`jest.config.js`) pins both vars to a **per-worker scratch dir** that is reset at the
start of every test file:
- Per-worker (`JEST_WORKER_ID`), reused and reset each file → bounded footprint (one
  dir per worker, no accumulation, no cross-file/run bleed).
- **Set-if-unset** → a test that pins its own dir (40+ already do) or the keyless
  integration wrapper (which deletes these vars to force self-skip) still wins.
- Opt-out for a HOME-fallback test is a plain `delete process.env.AMICUS_CONFIG_DIR`
  (already the house idiom).

`tests/hermetic-baseline.test.js` is the meta-test: with no per-test setup, config/keys
reads must resolve under `os.tmpdir()`.

**Caveat (state it in the CHANGELOG):** this closes the **config/keys-dir** door only.
It does **not** sandbox `os.homedir()`-based reads (OpenCode `auth.json`) — a `setupFiles`
env write cannot move `os.homedir()`. That credential door is already handled for the
paid tier by the parent-process scrub in `scripts/run-integration-keyless.js`.

**Blast radius (verified):** exactly one test file (`tests/local-providers.test.js`)
injected config via the HOME fallback without clearing the override; its `withConfig`
helper now opts out explicitly. Full unit suite: 375 suites / 4540 passed / 7 skipped /
0 failed.

## Item 5 — cosmetic cleanups

- `src/utils/env-loader.js`: delete the redundant second `loadEnvEntries()` re-read; the
  outer `fileEntries` (already in scope) holds identical, fully-migrated content.
- `tests/build-provider-models-local.test.js` and `tests/local-providers.test.js`: add
  `afterEach`/`finally` `rmSync` cleanup so the `bpm-*` / `lp-*` scratch dirs no longer
  leak (same leak class the hermetic baseline is careful to avoid).
