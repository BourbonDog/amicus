# Amicus v4.1 — "The skill sheds the ritual" (Design)

**Status:** DRAFT — awaiting Christian's review
**Baseline:** v3.2.3, main `aa2440b`, plus the finalized v4.0 spec
(`2026-07-19-v4.0-headless-council-engine-design.md`) — v4.0 lands first and its contracts are
authoritative inputs here.
**Inputs:** `docs/ROADMAP.md` v4.1 entry (locked 2026-07-19); v4.0 spec §2/§13/§14 (debate +
skill fast path explicitly deferred to this rev); `skills/second-opinion/SKILL.md` +
`COUNCIL-DESIGN.md` §12.3 + `SEAT-BRIEFS.md` (rebuttal templates); enhancement-council
proposals F1 (the "collapses the daily manual 6-stage ritual" half not consumed by v4.0).
**Release:** ships as **v4.1.0** (minor — everything here is additive; see §8 and OQ-7).

## 1. Goal

Two locked features:

1. **Skill fast path** — the second-opinion skill stops manually orchestrating Stages 1–3 and
   the artifact materialization half of Stage 5. One `amicus council run` invocation (CLI; or
   `amicus_council_run` + `amicus_wait` in Cowork/no-Bash contexts) replaces them. The human
   stages stay Claude-orchestrated: **Stage 0** intake (bench/chair via `council stats`, cost
   disclosure, optional-elements menu, launch confirmation), **Stage 4** accept/deny/modify
   decisions on the engine's `tally.json`, **Stage 6** approval-gated MODEL-NOTES lessons.
   `report.md` prose stays Claude-authored over the engine's artifacts.
2. **Debate mode headless** — the engine gains Stage 2.5 per the v4.0 deferred-scope note:
   `--debate` on `council run` / `debate` on `amicus_council_run`; provisional no-ledger tally →
   DEFEND/AMEND/WITHDRAW raiser solos → re-vote fanout for disputing judges → final tally with
   ledger; exactly one round; strict trailing-JSON briefing/parse contracts mirroring the v4.0
   Stage-2 style.

The benefit: the daily interactive council goes from ~30 hand-driven tool calls (2 waves + N
solos + validate/repair loops + tally assembly + chair call) to **one engine call plus the three
human stages** — same mechanics, same artifacts, same ledger, dramatically less ritual and less
orchestrator drift.

## 2. Non-goals

- **No change to the council's semantics.** Tiers, peers-only cascade, street-cred,
  anonymization rules, ledger policy, and the Stage-4 decision vocabulary are untouched. The
  engine executes the same contract the skill prose executed.
- **Stage-4 automation** — the engine stays report-only (v4.0 locked decision 4). The single
  mechanical exception, debate-mode withdrawals, is *recorded as fact* by the engine and
  *acted on* (auto-denied) by consumers (§5.6).
- **1-model scale-down** stays manual (solo `amicus start --no-ui --json`, Claude synthesizes,
  no tiers) — the engine requires ≥2 seats and single-pass has no council mechanics to shed.
- **Policy packs / run profiles** (v4.7), **local providers** (v4.2), **watch/streaming**
  (v4.5), **`--dry-run` cost preview** (backlog), **parallel panels** (COUNCIL-DESIGN §12.5).
- **No new MCP status tools** — tool-count discipline holds; v4.1 adds zero new tools (only
  new inputs on `amicus_council_run` and `amicus_verdict`).
- **No interactive/GUI debate** — debate is a headless engine feature surfaced through the
  skill; the Electron surface waits for v4.6.

## 3. Locked inputs (v4.0 contracts this design builds on)

Authoritative and assumed landed:

- `amicus council run` CLI shape: `--prompt-file` (required), `--council <preset> | --models`
  (XOR, ≥2 seats), `--chair` (default `deepseek`, must not be a bench seat), `--critic` (must be
  a bench seat), `--lenses` (count == seats, forces no-ledger; mutually exclusive with
  `--critic`), `--out-dir` (default `./council-<runId>/`), `--json`, `--max-cost` (whole-run
  ceiling checked before each paid stage), `--timeout` (per-leg), `--gateway`,
  `--no-validate-model`.
- Exit codes: 0 full / 1 pre-spend or fatal (`council_quorum`, `cost_exceeded`) / 2 degraded
  (thin judges, chair fail, `overallVerdict:null`) / 130/143 aborted — plus the degradation
  table, chair fallback promotion, and 2-repair judge / 1-repair chair caps.
- Run directory layout: `briefing-stage1.md`, `review-<model>.md ×N`, `bundle-stage2.md`,
  `judge-<model>.md ×N`, `chair-packet.md`, `chair-output.md`, `tally-input.json`, `tally.json`,
  `verdict.json`, `report.html`, `run.json` (schemaVersion 2, type `council-run`, stage
  checkpoints), `_scratch/` — with a sessions-dir pointer file so `status`/`wait`/`list`/`abort`
  resolve council runIds.
- Engine modules: `src/council/run.js` (state machine), `briefings.js`, `anonymize.js`,
  `parse-stage2.js`, `run-state.js`, `run-launch.js` (Plan-agent default, `--no-context`,
  `_scratch` judge cwd), `src/cli-handlers-council-run.js`; existing primitives
  (`validateFindings`, `tally()`, `buildVerdict`, renderers, ledger) consumed unchanged.
- Stage-2 judge trailing-JSON contract (`{ranking, adjudications}`), chair `VERDICT:` line
  parse, **chair verdict scale always on headless**, `meta` pins (`runType:'headless'`,
  `claudeInCouncil:false` — amended by this design, §4.4), fenced MCP council JSON,
  `amicus_council_run` (15th tool) returning `{runId, runDir}` async.
- Council Review Action v2 (`fail_on`, check-run annotations from Confirmed findings, evidence
  artifact).

Where this spec says "engine", it means that v4.0 machine; v4.1 extends it in place.

## 4. Design — Feature 1: skill fast path

### 4.1 Approaches weighed

**(a) Fast path primary; manual orchestration extracted to a companion reference file
(recommended).** SKILL.md keeps Stages 0/4/5/6 plus one compact "engine run" section; the full
manual Stage 1–3+5 mechanics (fanout commands, validate/repair loop, bundle assembly, tally
recipe, chair packet, PS 5.1 caveat) move verbatim-ish to a new
`skills/second-opinion/MANUAL-ORCHESTRATION.md`, referenced from SKILL.md as the documented
fallback. Docs-drift pins on the moved prose re-point to the new file (§4.9).

**(b) Fast path replaces manual entirely (delete the ritual).** Smallest SKILL.md, but it
deletes the only path that works when the engine itself is the thing misbehaving, the only home
for fully custom per-seat briefs (see OQ-3), and seven runs' worth of battle-tested operational
detail — the week after the engine's first release is exactly when a fallback is most likely to
be needed. Rejected.

**(c) Both paths inline in SKILL.md.** Keeps everything discoverable but the file stays
~550+ lines of two interleaved workflows; an orchestrating Claude that has run the ritual before
will keep running it out of pattern-match habit, which defeats the release. Rejected.

Recommendation: **(a)** — see OQ-1.

### 4.2 The new stage map

| Stage | Owner | Fast-path behavior |
|---|---|---|
| 0 — Intake & prep | Claude | Unchanged in substance: confirm material/analysis/criteria; create run folder `output/<stem>-council/`; prep material; pick bench + chair via `amicus council stats` + MODEL-NOTES; estimate cost; present the optional-elements menu; **author the briefing file** (§4.3) and, when Claude-in-council is ON, author `review-claude.md` (§4.4); **engine preflight probe** (§4.7); disclose run shape; wait for confirmation. |
| 1–3 (+5 artifacts) — The engine run | Engine | ONE `amicus council run` call (§4.5). Engine executes reviews → validate/repair → anonymize → judge wave → (debate, §5) → tally (+ledger) → chair → undecided `verdict.json` + `report.html`, checkpointing `run.json`. Claude waits (background CLI notify / `amicus_wait`), then reads `run.json` + exit code and **discloses any degradation** (§4.6). |
| 4 — Tiered decisions | Claude + user | Reads `<run-folder>/tally.json`. Presents Confirmed as bulk, Disputed/Contested/Singleton individually — unchanged vocabulary. Debate withdrawals are auto-recorded `denied`, never presented (§5.6). Thin-confidence `tierOverride` judgment retained. Writes `decisions.json`. |
| 5 — Outputs | Claude | Apply accepted findings → `<stem>-reviewed.<ext>` (unchanged). Then `amicus council verdict <run-folder>/tally.json --decisions <run-folder>/decisions.json -o <run-folder>/verdict.json --render` — the **decided** verdict replaces the engine's undecided one and `--render` (new, §4.5c) refreshes `report.html` in place. Assemble `report.md` (Claude-authored: chair synthesis + decision log + run-stats table now read from `run.json`/`tally.json` instead of hand-collected wave docs) with the `council report --md` stdout section as today. Present verdict inline; lead with `report.html`. |
| 6 — Lessons | Claude + user | Unchanged flow. Note: **the engine's finalize tally already appended the ledger row(s)** — the skill never re-runs `council tally` (double-append hazard); conformance per model is read from `run.json`/`tally.json` `runStats`. MODEL-NOTES diff stays approval-gated via the run-folder diff file. |

The Stage-0 optional-elements menu shrinks from five items to four: **chair verdict scale is
standard in the fast path** (the engine mandates the `VERDICT:` line headless — v4.0 locked
decision 1); the menu notes it as now-standard instead of offering it (OQ-5). Critic seat →
`--critic <model>`; expert lenses → `--lenses s1,s2,…`; debate mode → `--debate`;
Claude-in-council → `--claude-review` (§4.4). The critic+lenses composition exception is now
enforced by the engine's own validation (v4.0 makes them mutually exclusive) — the menu text
carries the same rule, so nothing new to reconcile.

### 4.3 The briefing contract — skill authors the WHAT, engine authors the HOW

The skill writes ONE briefing file, `<run-folder>/briefing.md` (kept, not `_tmp-` — it is run
provenance; the engine's composed `briefing-stage1.md` derives from it). Its contents are only
the review request:

- the material (inline if small/clean; else the absolute path of the extracted clean-text file —
  Stage-1 seats run agentically in the invoking cwd and can read referenced files, unchanged),
- the analysis request,
- the criteria,
- any material-specific cautions (e.g. "the appendix is out of scope").

Everything that is stage *mechanics* — the anti-sycophancy clause, the findings-JSON output
contract, judge tasks, no-tools preambles, chair packet, verdict-scale addendum — is the
engine's (`briefings.js` templates, per v4.0). The skill briefing must NOT restate output
contracts; duplicated contracts drift.

**Date stamping moves engine-side (small v4.1 addition):** `briefings.js` prepends
`Today's date is YYYY-MM-DD.` to every composed model-facing briefing (Stage-1 seat/critic/lens,
Stage-2 bundle, debate defense/re-vote, chair packet). This deterministically kills the false
"future-dated blocker" class MODEL-NOTES documents. The skill's Stage-0 rule softens to "state
the artifact's temporal context when relevant; the engine stamps today's date automatically."

### 4.4 Claude in the council — the hybrid contract

The engine pins `claudeInCouncil:false` (v4.0 §5) because headlessly there is no Claude. When
the skill's toggle is ON, Claude's own review cannot come from the engine. Two contracts weighed:

**(a) Review-as-input-file (recommended): `--claude-review <path>` / MCP `claudeReviewFile`.**
Claude authors its **fresh** Stage-1 review (prose + trailing findings JSON, identical contract)
as `<run-folder>/review-claude.md` *before* launch, and passes it to the engine. Engine behavior:

- **Pre-flight validation** via `validateFindings` — invalid file → error doc
  `council_claude_review_invalid`, exit 1, **before any spend** (the orchestrator authored it;
  it gets no repair loop — fix and relaunch is free).
- The review joins the anonymized Stage-2 bundle as one more labeled entry; its findings get
  run-global ids and enter every judge's adjudication set. `anonymize.js` already handles
  N labeled reviews; this is review N+1 sourced from a file instead of a leg.
- `meta.claudeInCouncil:true`; `'claude'` added to `meta.models` (the street-cred universe —
  exactly what the manual skill did); `runStats` gains
  `{model:'claude', role:'claude', status:'complete', durationMs:null, usage:null,
  conformance:'clean'}` — nulls per the never-invent rule.
- Claude **never judges** (no judge leg launched for it) and **never chairs** —
  `--chair claude` (any alias resolving to an Anthropic model is out of scope; the literal
  guard is on the reserved seat name `claude`) is a pre-flight error, same envelope as
  chair-in-bench.
- The chair packet includes the de-anonymized Claude review like any other; `tally()` computes
  Claude's peers-only street-cred from the judges' rankings unchanged — the "How Claude's
  review fared" readout falls out of the normal artifacts (`withSelf == peersOnly` since Claude
  casts no rankings).
- "Always fresh" stays a skill-side rule (the engine cannot verify freshness).

**(b) Claude-in-council keeps the manual path.** Zero engine change, but the toggle — a marquee
element — would drag every such run back into the full ritual, and the fast path's value
evaporates exactly when the user is most engaged. Rejected as the default; it remains what
happens on an engine too old for the flag (§4.7).

Recommendation: **(a)** — see OQ-2. Timing asymmetry (Claude's review is authored before the
bench runs) is not a leak: Stage-1 reviews are independent by design, and Claude holding the
label map is the same §5.4 asymmetry as today.

### 4.5 CLI/MCP contract changes (engine deltas for the fast path)

a. **`--claude-review <path>`** on `council run`; **`claudeReviewFile`** on
   `amicus_council_run`. Semantics per §4.4. Amends the v4.0 meta pin to: *claudeInCouncil is
   false unless `--claude-review` is provided.*
b. **`--no-cost-gate` passthrough** on `council run` (+ MCP `noCostGate`). v4.0's contract
   lists only `--max-cost`; the skill's "user asked for o3 by name" path needs the per-leg
   price-threshold gate disabled for the *whole* run in one place. The flag is forwarded to
   every internal launch (Stage-1 wave, repair solos, Stage-2 wave, debate solos/wave, chair) —
   this single-invocation posture replaces the skill's old "pass the same flag on every repair
   re-prompt and the chair call" footgun outright.
c. **`--render` on `council verdict`** (+ `render:true` on MCP `amicus_verdict`): after writing
   the decided `verdict.json`, re-runs the deterministic renderer to refresh `report.html` next
   to it, and (MCP only) returns the `--md` rendering in the tool result so Cowork sessions can
   assemble `report.md` without Bash. Without this, a Cowork fast-path run would end with a
   stale, pre-decision `report.html` as "the default artifact to hand the user". CLI users may
   still run `council report --md` for the markdown section (pinned strings unchanged; `--render`
   appends after the pinned argument tail, so the B22 regex still matches).
d. `--debate` / `debate` — Feature 2 (§5).

Everything else the skill used to pass per-call (`--agent Plan`, `--no-context`,
`--summary-length verbose`, background handling, `_scratch` judge cwd) is engine-internal per
v4.0 — the skill stops passing or mentioning them outside the manual reference.

**Canonical fast-path launch (shell contexts):**

```
amicus council run --prompt-file <run-folder>/briefing.md \
  --models "<m1,m2,m3>" --chair <chair> --out-dir <run-folder> --json \
  [--critic <m>] [--lenses s1,s2,s3] [--debate] [--claude-review <run-folder>/review-claude.md] \
  [--max-cost <$> | --no-cost-gate] [--timeout <min>] [--gateway …]
```

Run in the background; quoted `--models` (PowerShell comma-split rule unchanged); free council =
`--council free` instead of `--models` (free-tier disclosures in Stage 0 unchanged; the engine's
repair loop + conformance marking absorbs the throttled-leg handling the skill used to narrate).

**Cowork / no-Bash contexts:** `amicus_council_run` `{briefingFile, models|council, chair,
critic?, lenses?, debate?, claudeReviewFile?, outDir, maxCost?|noCostGate?, timeoutMinutes?,
gateway?}` → `{runId, runDir}` immediately; then `amicus_wait` with the runId (re-call while
`timedOut:true`; `amicus_status` fallback shows stage progression via the pointer file);
artifacts are then read from `runDir` with host file tools; Stage 5 uses `amicus_verdict` with
`render:true`. Council briefings remain self-contained, so MCP transport stays equivalent.

### 4.6 Degradation handling in the skill

The engine owns degradation (v4.0 table + §5.7); the skill owns **disclosure and user choice**.
The ~60 lines of per-stage wave-degrade prose collapse to one rule set keyed on exit code:

- **0** — proceed to Stage 4.
- **2** — read `run.json` stages + `tally.json` (`judged` flag) + `verdict.json`
  (`overallVerdict`): name every dead leg/stage and its error; apply the existing disclosure
  vocabulary (2-survivor runs → thin-ranking disclosure; chair-failed → the report carries no
  chair verdict — offer a solo re-chair via the manual path or proceed report-only); debate
  degradations per §5.7. Then proceed to Stage 4 with what exists.
- **1** — nothing usable was produced (quorum/cost/validation): present the error doc; offer
  re-run (possibly smaller bench), a raised `--max-cost`, or the manual/single-pass fallback.
- **130/143** — aborted; offer resume-as-new-run.

The engine never silently degrades (every degradation is in `run.json`); the skill never
presents a degraded run as clean.

### 4.7 Fallback rules + engine preflight

Stage 0 runs one probe before disclosing the run shape: `amicus council run` requires CLI
≥ 4.1 (`--claude-review`/`--debate`) or ≥ 4.0 (plain runs). Probe = `amicus --version` (CLI on
PATH) or the presence of the `amicus_council_run` MCP tool (Cowork). On too-old-or-missing:

1. Prefer `npx -y amicus@latest council run …` (the existing transport rule — npx always has
   the current engine; the known npx-cache-copy skew makes the *version probe* mandatory rather
   than optional).
2. Else fall back to **manual orchestration** (`MANUAL-ORCHESTRATION.md`) and say so.

Manual fallback is also the documented route for: fully custom per-seat briefs beyond
critic/lenses (OQ-3), deliberate mid-stage inspection/intervention, and engine-misbehavior
recovery. The 1-model scale-down is its own (retained, tiny) SKILL.md path — solo
`start --no-ui --json`, no engine involved.

## 5. Design — Feature 2: debate mode headless (Stage 2.5 in the engine)

Semantics are locked by SKILL.md Stage 2.5 + COUNCIL-DESIGN §12.3: provisional no-ledger tally →
one defense mini-wave → one re-vote mini-wave → final tally with ledger; **exactly one round**;
withdrawals stay in `findings[]`; missing/unparseable responses mean the original stands; dead
legs are never re-run. What v4.1 designs is the headless realization.

### 5.1 State machine (src/council/run.js) and run.json checkpoints

Without `--debate`, the v4.0 stage sequence is unchanged. With it, between Stage 2 parsing and
the chair:

```
stage2 → tally-provisional → [debate-defense → debate-revote] → tally-final → chair → verdict → report
```

- **`tally-provisional`** — in-process `tally()` on the assembled input, **no ledger append**;
  written to `tally-provisional.json` (audit artifact). If Contested + Disputed == 0 (or
  `judged:false` — a <2-judge run has no adjudication surface): skip both debate waves, run the
  finalize step on the unchanged input, and record `debate.outcome:'nothing-to-debate'`.
- **`debate-defense`** — group Contested + Disputed findings by raiser; one concurrent headless
  solo per raiser (run-launch wrappers; `_scratch` cwd like judges — a tool-capable raiser must
  not read the de-anonymized run dir), briefing per §5.3. Raw outputs materialized as
  `rebuttal-<model>.md`; parsed per §5.4; taskIds checkpointed.
- **`debate-revote`** — build ONE shared re-vote bundle (`revote-bundle.md`) holding every
  *defended or amended* finding + its anonymized defense (withdrawn findings never appear).
  Recipients: exactly the judges whose Stage-2 adjudications contain ≥1 `dispute` on any
  bundled finding. Zero recipients or zero defended/amended findings → skip the wave. One
  fanout; raw outputs `revote-<model>.md`; waveId checkpointed.
- **`tally-final`** — reassemble the tally input (§5.5) and run `tally()` **with ledger append**
  (unless `--lenses` — the lens no-ledger rule wins, unchanged), write `tally.json`. This final
  record is what the chair packet, verdict, and report consume. The provisional record is never
  ledgered; an aborted run never reaches `tally-final`, so aborted runs never ledger — matching
  the manual skill's finalize-only append.
- **Chair** — packet gains a conditional "Debate round outcomes" section (§5.3c).

`run.json` `stages[]` gains the three new entries with the standard
`{name, status, startedAt, completedAt, taskIds?/waveId?}` shape, plus a top-level additive
`debate` summary: `{enabled, outcome:'ran'|'nothing-to-debate'|'skipped-cost-ceiling',
contested, disputed, defended, amended, withdrawn, noResponse, revoteJudges, revoteApplied,
verdictChanges}`.

### 5.2 CLI / MCP surface

- `amicus council run --debate` — boolean. Composes with `--critic` (a critic's findings can be
  contested; it simply gets a defense solo) and with `--lenses` (final tally stays no-ledger).
  No interaction with `--chair`.
- `amicus_council_run` gains `debate?: boolean`.
- Council Review Action v2 gains input `debate` (default `false`) → forwards the flag; its
  annotation step excludes findings with `debate.action === 'withdrawn'` and the sticky comment
  gains a "Withdrawn in debate" collapsible (OQ-6).
- `--timeout` (per-leg) and `--gateway` forward to debate legs like any other.

### 5.3 Briefing templates (briefings.js) — strict trailing-JSON contracts

Adapted from SEAT-BRIEFS.md's line-based rebuttal templates, hardened to the v4.0 Stage-2
trailing-JSON style (prose first, one fenced ```json block last, nothing after it). All open
with the no-tools preamble and the date stamp (§4.3).

**a. Defense solo** (one per raiser; body after preamble + date):

> You reviewed an artifact and raised the findings below. Peer reviewers (anonymous) disputed
> them for the stated reasons. For EACH finding decide: DEFEND it with evidence, AMEND it with
> corrected replacement text, or WITHDRAW it. Withdraw anything you cannot defend with
> evidence — an unsupported repeat of the original claim is weaker than a withdrawal.
>
> *[one block per finding: run-global id · claim · severity · location · the peers' dispute
> reasons, anonymized — no judge identities]*
>
> End your response with a fenced ```json block, with no text after it:
>
> ```json
> {
>   "responses": [
>     {"id": "A1", "action": "defend", "argument": "<strongest evidence-based defense, one paragraph max>"},
>     {"id": "A3", "action": "amend", "claim": "<full corrected replacement claim>", "argument": "<why, one sentence>"},
>     {"id": "B2", "action": "withdraw"}
>   ]
> }
> ```
>
> Every listed finding id must appear exactly once. `defend` requires `argument`; `amend`
> requires `claim`; `withdraw` requires neither.

**b. Re-vote bundle** (one shared document, fanout to disputing judges):

> You previously adjudicated findings on this artifact and disputed at least one of those
> below. The (anonymous) raiser has now responded. Re-adjudicate ONLY the findings listed, in
> light of each response. Changing your verdict when the defense is convincing is good judging,
> not weakness; so is holding your dispute when it isn't.
>
> *[one block per finding: run-global id · claim (marked **AMENDED**, with the replacement
> text, when amended) · severity · the raiser's defense argument]*
>
> End your response with a fenced ```json block, with no text after it:
>
> ```json
> {
>   "revotes": [
>     {"id": "A1", "verdict": "agree", "reason": "<one line>"},
>     {"id": "A3", "verdict": "dispute", "reason": "<one line>"}
>   ]
> }
> ```
>
> `verdict` is one of `agree | dispute | neutral`. Every listed finding id must appear exactly
> once.

**c. Chair packet addendum** (only when debate ran): a "Debate round outcomes" section listing,
per contested/disputed finding: original claim → defense action (defended / amended with both
texts / withdrawn / no response) → per-judge re-vote changes (before → after). Built from
`debate.json` + both tally records; de-anonymized like the rest of the packet.

### 5.4 Parsing (parse-stage2.js extensions)

Shared last-JSON-block extractor; two new parsers, both returning per-id tri-state results:

- `parseDebateDefense(text, expectedIds)` → per id: `{action:'defend'|'amend'|'withdraw',
  argument?, claim?}` when the entry is present and valid (enum ok; `defend` ⇒ non-empty
  `argument`; `amend` ⇒ non-empty `claim`); else `{action:'no-response'}` (original stands).
  Unknown ids are ignored. Whole block missing/unparseable → **1 repair re-prompt** (solo,
  quoting the errors, v4.0 repair pattern) → still bad: every expected id `no-response`, leg
  recorded `conformance:'unstructured'`.
- `parseRevote(text, expectedIds)` → per id: `verdict` + optional `reason`; missing/invalid
  entry → original verdict stands; unknown ids ignored; whole-block failure → **1 repair** →
  originals stand, `conformance:'unstructured'`.

One repair (vs the judges' two) is deliberate: every debate parse failure has a benign,
spec-mandated fallback ("the original stands"), unlike a dropped judge which loses adjudication
data — one repair bounds the paid-stage tail where the downside is smallest.

`debate.json` artifact records the parsed outcomes:
`{findings:[{id, raiser, action, argument?, claim?, previousTier}],
revotes:[{judge, id, verdict, reason?, applied}]}`.

### 5.5 Final tally reassembly (new pure module src/council/debate.js)

Keeps `run.js` under the line gate; pure functions, DI-free:

- **Amend:** replace the finding's `claim` text; `id`, `raiser`, `severity` unchanged (`tally()`
  only needs id/raiser/severity — the claim rides along for the chair/report).
- **Withdraw:** the finding **stays in `findings[]`**; its existing adjudications stand; the
  final cascade assigns whatever tier falls out. Engine decorates it (§5.6).
- **Re-vote application:** for each re-vote wave judge J and bundled finding F with a valid
  re-vote, J's adjudication entry on F is **replaced** (agree/dispute/neutral). This mirrors the
  manual contract exactly — a wave judge re-votes every bundled finding, including ones it had
  not disputed (legs are stateless; a shared fanout bundle cannot personalize per judge).
  *Rejected alternative:* apply a judge's re-vote only where it originally disputed — tighter,
  but it requires per-judge bundles (N solos, N briefings) or asks stateless legs to remember
  votes they never saw, and it diverges from the documented skill semantics the bench has
  already operated under.
- **Raiser self-votes:** if a raiser is also a re-vote judge and re-votes its own bundled
  finding, the entry is included as-is — `tally()` already excludes raiser self-votes from the
  peers-only cascade (no pre-filtering, v4.0 rule).
- Rankings and `runStats` carry over; `runStats` gains the debate legs
  (`role:'rebuttal'`/`role:'revote'`, normal status/duration/usage/conformance). Ledger rows
  stay one per (run × model) — appendRun keys off `meta.models`, so extra legs don't
  double-count.

### 5.6 Withdrawals downstream — report-only, mechanically marked

The engine stays report-only (v4.0 locked decision 4), so it does **not** write decisions. It
records the *fact*: each final-tally finding gains an additive
`debate: {action: 'defended'|'amended'|'withdrawn'|'no-response', previousTier}` object
(engine-injected into the record before writing `tally.json`; carried through `buildVerdict`
into `verdict.json`; council family stays schemaVersion 2 — additive fields only). Consumers
apply the rule:

- **Skill Stage 4:** findings with `action:'withdrawn'` are auto-entered in `decisions.json` as
  `{"id", "decision": "denied"}`, never presented; listed in `report.md` under "Withdrawn by
  raiser (debate mode)" — exactly the current SKILL.md contract, now driven by engine metadata.
- **Action v2 / CI:** withdrawn findings are excluded from check-run annotations and listed in
  their own collapsible.
- **Renderers:** `report.js`/`report-html.js` gain a small conditional "Debate round" section
  (withdrawn list + tier movements `previousTier → tier`) when the metadata is present —
  deterministic data only.

### 5.7 Degradation, exit codes, cost ceiling

Extending the v4.0 table (debate rows only; all other rows unchanged):

| Condition | Behavior | Exit |
|---|---|---|
| Nothing to debate (0 Contested+Disputed, or `judged:false`) | skip both waves; finalize on unchanged input (ledger on); `debate.outcome:'nothing-to-debate'` | unchanged (0 path) |
| Defense solo dead, or unstructured after 1 repair | that raiser's bundled findings: `no-response` — originals stand; run continues | 2 |
| Re-vote wave partial | surviving judges' re-votes apply; dead judges' originals stand | 2 |
| Re-vote wave fully dead | all originals stand; defenses still reach the chair packet | 2 |
| Cost ceiling hit before the defense wave | skip debate entirely; finalize provisional input (ledger on), `debate.outcome:'skipped-cost-ceiling'`; then v4.0 ceiling rules (no chair, `overallVerdict:null`) | 2 |
| Cost ceiling hit after defense, before re-vote | skip re-vote; amendments + defenses apply, originals stand; finalize (ledger on); no chair | 2 |
| Abort mid-debate | v4.0 abort path; no `tally-final`, **no ledger append** | 130/143 |

Debate stages are **paid stages**: the `--max-cost` pre-launch check runs before the defense
wave and again before the re-vote wave (the v4.0 checked-stage list grows to: Stage-1 wave,
repair solos, Stage-2 wave, defense solos, re-vote wave, chair solo). In-flight debate legs are
never aborted for cost. Exactly-one-round is structural: the state machine has no edge back
into a debate stage.
